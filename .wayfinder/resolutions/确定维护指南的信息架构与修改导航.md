# 确定维护指南的信息架构、修改导航与故障边界

## 决策

选择原型 **B 增强版“系统分层优先”**。`docs/维护.md` 应先帮助维护人员从 GitHub 完整获取受控项目，再建立系统架构、权威边界、文件接口和模块地图；随后提供面向 LLM 编码的最小上下文、按修改意图导航、测试发布、故障诊断和恢复步骤。

原型保留在：[`../prototypes/维护指南信息架构原型.html?variant=B`](../prototypes/维护指南信息架构原型.html?variant=B)。

选择理由：后续维护人员很可能使用 LLM 阅读和修改代码。仅给“改什么去哪里”的捷径不足以防止局部误改；维护人员和 LLM 都需要先理解工作簿业务状态、仓库程序权威、模块接口、状态写入、跨模块调用链和 Office 部署限制。方案 B 同时吸收：

- 方案 A 的“修改意图 → 首要入口 → 连带影响 → 验证”快速索引；
- 方案 C 的业务确认门、恢复点、技术验证和业务放行四个变更关卡。

## 一、目标阅读路径

### 首次接管

1. 从 GitHub Clone 或 Fork 项目，核对远程、分支、提交和受跟踪资源。
2. 理解 Git 获取的是源码、静态资源和工作簿快照，不等于取得内网最新业务状态与备份。
3. 阅读系统总览：三类权威、内外网数据流、文件接口和三个主调用链。
4. 按目录阅读模块地图，理解每部分的职责、公开入口、读写状态、错误模式和验证方式。
5. 阅读 VBA 同步、Office 环境、Git 分支和发布流程。
6. 开始具体修改时，再从“按修改意图导航”进入对应章节。

### 使用 LLM 修改代码

1. 先向 LLM 提供 `AGENTS.md`、维护指南中的系统总览和目标模块章节。
2. 根据模块章节列出的“LLM 最小上下文”读取相关源码、共享接口和调用方，不把整个仓库无差别塞入上下文。
3. 要求 LLM 先复述权威数据、调用链、状态写入和业务确认点，再提出修改方案。
4. 只修改仓库源码或受控资源，不直接修改 VBE、正式输出或未经授权的业务事实。
5. 要求 LLM 报告修改文件、影响面、编码检查、自动验证、仍需人工执行的 Office/业务验收和回滚点。

### 日常查找

首页应提供四个直接入口：

- 项目获取、Fork 与同步；
- 系统架构和模块地图；
- 修改某类需求从哪里开始；
- 故障诊断、发布与恢复。

## 三、Git 获取与协作必须说明的事实

当前权威远程为：

```text
https://github.com/EternalPneuma/nav_vba_minimal_dependency.git
```

核实时它是公开 GitHub 仓库，默认分支为 `master`，本地 `origin` 的 fetch/push 均指向该地址。正式维护指南不应写死易过期的提交号，而应教维护人员运行：

```powershell
git remote -v
git branch -vv
git status -sb
git log -1 --oneline
```

文档必须分别提供两种协作路径：

### 有原仓库写权限

```powershell
git clone https://github.com/EternalPneuma/nav_vba_minimal_dependency.git
cd nav_vba_minimal_dependency
git switch -c maintenance/<主题>
# 修改、验证、审查
git add <明确文件>
git commit -m "<修改说明>"
git push -u origin maintenance/<主题>
```

随后通过 Pull Request 合并到 `master`，不鼓励直接在 `master` 上试改。

### 无原仓库写权限

在 GitHub Fork 后，个人仓库作为 `origin`，原仓库作为 `upstream`：

```powershell
git clone https://github.com/<用户名>/nav_vba_minimal_dependency.git
cd nav_vba_minimal_dependency
git remote add upstream https://github.com/EternalPneuma/nav_vba_minimal_dependency.git
git switch -c maintenance/<主题>
git push -u origin maintenance/<主题>
```

同步原仓库：

```powershell
git fetch upstream
git switch master
git merge --ff-only upstream/master
git push origin master
```

文档必须提醒：

- `git clone` 只能取得已提交、已跟踪内容；本地暂存、未提交或被忽略文件不在远程。
- Git 中的主工作簿只是某次已提交快照，不能自动代表内网最新业务数据。
- 181、REITs、浏览表、生成输出和 `backup` 默认不属于源码获取范围。
- 发布前要用 `git ls-files` 或清单核对 VBA、固定图片、四个图表模板、两份一页通 PPT 模板和主工作簿快照。
- 不应使用 `git add .` 无差别纳入工作区，尤其仓库含业务工作簿、输出和截图时；应明确添加文件并审查 `git diff --staged`。

## 四、模块地图的表达单位

每个模块目录都采用同一结构，不逐私有函数解释源码：

1. **为什么存在**：它隐藏了什么复杂性，向调用方提供什么能力。
2. **公开接口**：主入口宏、调用前置条件、顺序要求和错误传播方式。
3. **读取什么**：工作表、配置表、同级输入、模板和上游输出。
4. **写入什么**：主工作簿状态、中间文件、正式交付物和临时文件。
5. **调用和被调用**：所在主调用链、共享接口及下游。
6. **关键不变量**：日期一致、代码唯一、配置启用、模板锚点等。
7. **典型错误模式**：足以指导诊断，不复制全部错误文字。
8. **修改时的最小验证**：自动检查、Office 重开和人工验收。
9. **LLM 最小上下文**：目标文件、共享接口、调用方、配置说明和相关测试／脚本。
10. **业务确认点与回滚点**。

模块说明应以接口、状态和影响链为中心。例如 `chart` 章不能只列四个文件，而应解释：绘图净值来源的浏览表优先规则、配置产品集合、产品汇总作为图表载体、按最新文件发现的日期风险，以及最终 PNG 被展示报表和推荐材料消费。

## 五、LLM 编码维护规范

维护指南应给出可复用的 LLM 任务结构：

```text
目标：要改变的可观察行为
事实依据：问题样例、基准日期、错误文字或验收差异
先读：AGENTS.md、维护指南目标章节、列出的最小上下文文件
权威边界：哪些工作表／配置／业务事实不能猜
约束：UTF-8、CRLF、CP936、临时工作簿副本、不得绕过同步保护
验收：自动检查、Office 验证、业务确认和回滚要求
输出：修改文件、原因、验证证据、未验证项目和风险
```

必须明确：

- LLM 可以阅读、定位、编辑仓库源码，执行静态检查和编写验证步骤。
- LLM 不得把 VBE 代码当作长期源码，不得直接修正式输出文件。
- LLM 不得自行决定开放日、产品范围、归属、启停、展示文字或业务结果是否可交付。
- LLM 不得绕过 CP936 guard，也不得把静态检查描述成已完成 Excel/PowerPoint 运行验收。
- 修改主调用链时，必须联查操作面板、批处理错误传播、显示名称和运行文档。
- 修改共享配置接口时，必须联查全部调用方，而不是只修当前报错模块。

## 七、故障诊断结构

故障章节按“用户可见症状”提供入口，而不是按文件名列错误：

| 症状组 | 第一诊断层 |
|---|---|
| 面板某一步失败 | 保存完整错误和步骤，映射到主调用链的第一个失败模块 |
| 日期、产品或数量不对 | 输入目录、181 增量边界、浏览表优先、配置产品集合 |
| 配置预检失败 | 权威工作表、六张命名表、代码唯一性和交叉引用 |
| 开放日阻断 | 区分业务事实未确认与算法／状态处理缺陷 |
| 图表、图片或展示错误 | 产品汇总 → 图表对象 → PNG → 最终输出逐层定位 |
| 一页通失败 | 静态预检 → 同日数据 → Excel 重开 → PowerPoint 锚点/OLE → 整批替换 |
| 推荐材料失败 | 产品范围 → 依赖写回 → 同日主题图片 → 资产流程 → 正式输出 |
| VBA 同步或乱码 | ACP、UTF-8/CRLF/CP936、VBE 信任、导入和读回差异 |
| 文件无法替换 | 输出占用、目录权限、临时／备份路径和旧文件恢复 |

统一诊断循环：

```text
记录现场
→ 判断输入／业务数据／代码／环境／输出占用
→ 停止扩大影响并建立副本
→ 在副本找到第一个错误层
→ 修复根因
→ 从受控恢复点重跑
→ 技术验证
→ 业务放行
```

## 八、技术处理与业务确认边界

### 必须交给业务确认

- 开放日及节假日顺延；
- 产品身份、归属、启停、系列、范围和展示顺序；
- 基准收益率、业务展示文字和模板业务内容；
- 输出产品数量是否符合本次交付要求；
- 最终 Excel、图片和 PPT 是否可以交付。

### 技术维护可以处理

- 源码、调用链、错误传播、路径和文件发现；
- 编码、同步、VBE 读回、Office 自动化和模板锚点；
- 数据导入实现、计算实现和格式实现；
- 在业务事实已确认后的配置录入与技术验证；
- 现场保全、工作簿副本、回滚和重跑。

### 必须停止的技术场景

- 无修改前工作簿副本；
- 需要猜业务事实才能继续；
- 影响范围或破坏性工具删除范围不清；
- 计划直接修正式输出或只在 VBE 修改；
- 非 CP936 环境准备绕过同步保护；
- 目录中“最新文件”是否属于本次基准日期无法确认；
- 只有静态检查，却准备宣称完成 Office 或业务验收。

## 九、发布、恢复和已知风险

发布章节使用四个不可越过的门：

1. **业务事实已确认**；
2. **恢复点已建立**；
3. **技术验证已完成**；
4. **业务结果已放行**。

必须覆盖：

- 使用临时工作簿副本运行 `sync-vba.ps1`；
- VBA 严格 UTF-8、CRLF、CP936 可表示和 PowerShell BOM；
- VBE 导入与读回全部成功；
- 按变更风险执行中间文件比较、数据摘要、Excel/PowerPoint 重开和目视检查；
- 审查 Git 工作区和暂存差异，使用功能分支和 Pull Request；
- 发布包核对两份一页通 PPT 模板及全部静态资源；
- 正式工作簿业务备份、回滚点和完整重跑。

已知限制集中维护，不分散复制：

- 工作簿业务数据没有自动事务回滚；
- 输出替换保护不完全一致；
- 单项宏按“最新文件”发现中间文件，存在日期串用风险；
- 浏览表存在时优先于内部 181；
- 回归脚本不验证样式、图表、图片和 PPT；
- Git 工作簿只是已提交快照，不等于内网最新业务状态；
- `backup` 的受控保管、保留周期和恢复责任尚待现场确定。

## 十、文档边界与防止源码复述

- `维护.md` 权威维护架构、模块接口、源码修改、LLM 协作、Git、同步、测试、诊断、恢复和已知限制。
- `运行.md` 权威维护普通运行人员的按钮步骤、人工检查和停止求助。
- `报表配置与操作手册.md` 权威维护业务配置字段、表间规则和配置操作。

维护指南可以链接源码，但不逐私有函数翻译。判断内容是否应该保留的标准是：它是否帮助维护人员确定接口、权威状态、影响面、验证或恢复；如果只是复述某一函数内部循环，应留在源码注释。
